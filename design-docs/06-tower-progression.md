# 06. 無限タワー構造・進行設計

担当範囲: ストーリー廃止に伴うゲーム構造の中核。無限階層 / 自動生成 / 敵スケーリング / 階層ボスゲート / 10層ごとのワープ / 全滅ペナルティ / 目的・スコア / システム解放トリガー

> 本ドキュメントは、当初の「ストーリー駆動ダンジョンRPG」から **「無限タワー型ローグライト」** への方針転換を反映した中核設計です。他ドキュメント（01〜05）の前提を上書きする箇所があり、その場合は本書を優先します。

---

## 1. ゲーム構造の概要

- **ストーリーは作らない**。プレイの動機は「より深く登ること」と「ビルドを磨くこと」。
- 迷宮は **上限のない無限階層のタワー**。1層進むごとに敵が徐々に強くなる。
- **10層ごとに区切り**があり、各区切りに **階層ボス** と **ワープチェックポイント** を置く。
- **階層に上限はない**（無限に登れる）。一方で **キャラクターのレベル上限は100**（[01](./01-character-system.md)）。育成の伸びしろは **転生**（レベル100到達後の作り直し＆ボーナス）・装備・スキル振りで確保し、無限に伸びる敵に対応する。
- 拠点（街）とタワーを往復しながら、装備・スキル・パーティを強化して到達階を更新していく。

### 確定した設計判断（ユーザー合意済み）

| 項目 | 決定 |
| --- | --- |
| マップ生成 | **自動生成・初回だけ固定**（一度入った階の地形は固定。再訪・手描きマップ・ワープが成立） |
| 全滅ペナルティ | **ソフト**（拠点に戻るだけ。キャラ・装備・所持金・アイテムのロストなし。失うのは潜行中の現在地＝そのダイブの進行のみ） |
| プレイ目的 | **最高到達階の更新**（スコアアタック）＋ **階層ボス撃破** ＋ **ビルド構築の追求** |
| バランス哲学 | **階層ボスで区切る中間型**（基本は育てれば進めるが、一定階ごとのボスが明確な壁になる） |

## 2. 階層生成（自動生成・初回だけ固定）

無限に階を用意するためプロシージャル生成を採用するが、**一度生成した階は地形を固定保存**する。これにより手描きマッピング（[02](./02-exploration-mapping.md)）と再訪・ワープが意味を持つ。

```ts
interface TowerFloor {
  depth: number;            // 階層番号（1, 2, 3, ... 無限）。これがフロアの正準キー [05 §0.5]
  seed: number;             // この階の生成シード（masterSeed から派生・固定保存）
  generated: FloorMaster;   // [02] のフロア構造。初回生成時に確定し保存（以後は再生成しない）
  isBossFloor: boolean;     // depth % BOSS_INTERVAL === 0
  encounterTier: number;    // 出現敵プールの帯（floor((depth-1) / BAND_SIZE)）
  // ▼ ランタイム消化状態（旧 foeStates を統合。[05] SaveData ではなくここに保持）
  foeRuntime: FoeRuntimeState[];          // [02 §6.2] FOEの現在位置・撃破フラグ
  openedChests: string[];                 // 開封済み宝箱の cellKey
  depletedGathers: string[];              // 枯渇した採集点の cellKey
  consumedEvents: string[];               // 消化済みイベントの id（oneShot 用）
}
```

- **生成タイミング**: その階に初めて到達したとき（ワープ先として初確定時を含む）に `seed = masterSeed の fork('floor:'+depth)`（[05 §0.4](./05-progression-meta.md)）を確定し、地形・配置を生成して `SaveData.towerState.floors[depth]` に保存。**保存後は `generated` を真実とし、二度と再生成しない**（マスターデータ更新で地形が変わる事故を防ぐ）。
- **再訪**: 保存済みなら同じ地形＋消化状態を再現。手描きマップ（`playerMaps[depth]`）・踏破情報（`exploredCells[depth]`）もそのまま使える。

### 2.1 生成アルゴリズム（方針確定・数値は暫定）

```ts
function generateFloor(depth: number, rng: Rng): FloorMaster
```

決定論的に動かすため、**乱数消費順を固定**する（[05 §0.4](./05-progression-meta.md)）。順序: ①地形 → ②階段 → ③採集点 → ④イベント → ⑤FOE → ⑥（ボス階なら）ボス。

1. **サイズ**（depth 依存・暫定式）: `size = clamp(15 + floor(depth/5), 15, 40)` を一辺に。正方形でなくてもよい。
2. **地形（迷路）**: MVP は **部屋＋通路法**（複数の矩形部屋をランダム配置→通路で連結）を推奨。穴掘り法・壁伸ばし法でも可。**辺の壁は隣接セルと必ず整合**させる（セルAの `E` 壁＝セルBの `W` 壁）。生成は `walls` を二重に持たず「辺集合」で管理し、両セルに反映する実装にする。
3. **到達可能性の保証（必須）**: 生成直後に **入口階段から全配置物（出口階段・採集点・イベント・ボス）へ到達可能か** をBFS/Union-Findで検証し、孤立があれば通路を追加 or 再生成。これを満たさない階は出さない。
4. **階段**: 入口（前の階からの上り）と出口（次の階への上り）を、互いに一定距離離れたセルに置く。ボス階の出口は §4 のゲート対象。
5. **配置物の個数（depth 依存・暫定）**: 採集点 `2 + floor(depth/10)`、イベント `0..2`、FOE `floor(depth/8)`（深いほど増。ボス階は除く）。配置候補は「通路/部屋の床セル」から重複なく抽選。
6. **仕掛け（FloorType）**: 深いほどダメージ床・暗闇・一方通行（[02 の FloorType](./02-exploration-mapping.md)）の出現率を上げる。
7. **ボス階の特例**: `isBossFloor` の階は **必ずボス部屋を1つ作り**、出口階段の手前に固定ボス遭遇を置く（§4）。雑魚FOEは置かない。

> **設計判断**: 「初回だけ固定」により無限性（プロシージャル）と世界樹の核（手描きマッピング）を両立。ワープで飛ばした階も後から手動で埋める動機が残る。アルゴリズム本体は `vitest` で「同一シード→同一 `FloorMaster`」「全配置物が到達可能」を固定テストする。

> **MVP 実装メモ（Phase 1・実装済み）**: 上記のうち実装済みは **①地形・②階段** まで。
> - **アルゴリズムは穴掘り法（再帰的バックトラッカ）を採用**（部屋＋通路法ではなく、§2.1 で許容された方式）。全域木になるため**全セルが相互到達可能**で、孤立修復の追加処理が不要。一本道を緩和するため壁を数枚だけ抜いてループを足す。
> - **サイズは MVP では `min(25, 15 + floor(depth/5))`** に調整（上限を 40→25 に。スマホ表示・生成負荷のため）。
> - **採集点・イベント・仕掛け床（③④⑥）は未配置**（地形＋入口/出口階段のみ）。乱数消費順は「①地形→②階段」で固定し、これらは将来この順の**末尾に追加**する（既存階の再現を壊さない）。
> - 実装: `domain/generateFloor`（純関数）＋ `domain/dive`（初回生成して `towerState.floors[depth]` に固定保存）。テスト済み（同一シード再現・全到達・壁整合・外周閉鎖）。

> **MVP 実装メモ（Phase 4-3・FOE 実装済み）**: ⑤FOE を実装。乱数消費は **②階段の後（末尾）** に追加し、既存階の再現を壊していない（generateFloor.test の決定論テストは不変）。
> - **配置数**: ボス階以外で `1 + floor(depth/8)`。設計式 `floor(depth/8)` だと第1〜7階に FOE が出ず「見える脅威」を導入できないため、**最低1体**は出すよう調整（難易度「少しハード」方針にも適合）。バランスは Phase 6 で再調整可。
> - **配置位置**: 入口から manhattan 3 以上離れた、イベントの無い床セルを抽選（最大20回試行）。`patrol:{kind:'wander'}`・`moveSpeed:1`・`sightRange:3`・`respawn:false` を既定とする。
> - **移動 AI（`domain/foe.ts` `stepFoes`）**: 「プレイヤー1歩＝全FOE1手」を `spawnId` 昇順で解決。感知→追跡（貪欲に manhattan を縮める1歩、壁=`canMove` を尊重）／非追跡は patrol（wander=rng で開口方向、charge=指定方向、static/loop=静止）。FOE 同士は同一セルに重ならない（occupied 管理）。接触でプレイヤーセルへは進入せず戦闘予約。
> - **先制/不意打ち（[03 §10]）**: プレイヤーから踏み込み＝先制（`firstStrike:'preemptive'`）、FOE がプレイヤー背後（`dir===playerDir`）から接触＝不意打ち（`ambush`）、正面/側面からの接触＝通常（`none`）。`battle.resolveTurn` がターン1のみ片側を行動不可にする。
> - **MVP 簡略化**: 感知は壁透過の manhattan 距離（[02 §6] の「壁で遮られなければ」は未考慮）。追跡は BFS ではなく貪欲（局所最適で詰まりうる）。床タイプ効果は FOE に適用しない。これらは将来精緻化の余地あり。
> - **戦闘決着**: 勝利で該当 FOE を `foeRuntime.defeated=true` にしてマップから消す（`dive.resolveFoeBattle`）。敗走/逃走では残置（再追跡）。FOE はマップ（探索済みセルのみ）と擬似3D（正面直線上）に自動表示。

## 3. 敵スケーリング（1層ごとに徐々に強化）

敵は「基準ステータス × 階層係数」で強くする。データ（基準値）とスケール関数を分離し、バランス調整を数値編集で完結させる。

```ts
// 各モンスターは基準階のステータスを持つ
interface EnemyMaster {
  id: string;
  baseStats: Stats;     // この敵の基準値
  refDepth: number;     // 基準階（この階で baseStats 等倍）
  tierBand: number;     // 主に出現する10層帯
  // ...属性耐性・スキル・ドロップ等
}

// 出現階に応じた係数。線形ベース＋帯ごとの微調整を推奨（暫定式）
function enemyScale(depth: number, refDepth: number): number {
  const k = 0.06; // 1層あたりの伸び（要バランス調整）
  return 1 + k * (depth - refDepth);
}
function effectiveEnemyStats(enemy: EnemyMaster, depth: number): Stats {
  const s = enemyScale(depth, enemy.refDepth);
  return scaleStats(enemy.baseStats, s);
}
```

- **敵プールの入れ替え**: 10層帯（`tierBand`）ごとに登場モンスターを入れ替え、係数で微調整する。係数だけで延ばすと見た目が単調になるため、帯ごとに新モンスター・新属性・新行動を投入する。
- **インフレ対策**: 係数を指数的に上げ過ぎると HP/ダメージの桁が破綻する。**線形〜緩やかな伸び**を基本にし、育成側（[01](./01-character-system.md)）の伸びと相対関係を保つ。表示桁・計算オーバーフローに注意。
- **乱数注入**: 出現抽選・ドロップ抽選は `Rng` 経由でテスト可能に。

> ⚠️ `k=0.06` 等の数値は **暫定**。実際のバランスは育成カーブとセットでプレイテストして決める（§9 の未決事項）。

### 3.1 暫定バランス定数（調整の起点・`src/data/balance.ts` に集約）

実装着手用の **暫定値**。プレイテストで上書きする前提だが、まずこの値で動かしてカーブの形を確認する。すべて1ファイルに集約し、マジックナンバーを散らさない。

```ts
export const BALANCE = {
  LEVEL_CAP: 100,
  BOSS_INTERVAL: 10,        // 何階ごとにボス階か（=ワープ間隔）
  BAND_SIZE: 10,            // 敵プール帯の幅
  ENEMY_SCALE_K: 0.06,      // enemyScale の1層あたり伸び
  // 成長（[01 §5]）: 素ステは線形。stat(Lv) = base + growth*(Lv-1)
  // 経験値（[01 §5]）: expToNext(Lv) = round(20 * Lv^1.6)（暫定・逓増）
  EXP_CURVE_BASE: 20, EXP_CURVE_POW: 1.6,
  // ダメージ（[03 §7]）: 除算型を採用
  DAMAGE_DEF_K: 100,        // dmg = base * K/(K+def)
  CRIT_MULT: 1.5, WEAK_MULT: 1.5, RESIST_MULT: 0.5,
  BACK_ROW_MELEE_MULT: 0.7, // 後衛の近接被弾/与弾減衰
  DMG_VARIANCE: [0.95, 1.05] as const,
  // ユニオン（[03 §9]）
  UNION_GAIN_PER_ACTION: [5, 15] as const, UNION_GAIN_ON_WIN: 15,
  // 下層ファーム減衰（[06 §9-7]）: 到達最深から離れた階ほどEXP/ドロップを減衰
  FARM_EXP_DECAY_PER_BAND: 0.85,
} as const;
```

> これらは「式の構造」を確定させるための起点。式の**形**（線形成長・除算型ダメージ・逓増EXP）は本書で確定し、**係数だけ**を後で調整する方針。各式の詳細は参照先（[01 §5](./01-character-system.md)・[03 §7](./03-battle-system.md)）に置く。

## 4. 階層ボスゲート（中間型バランスの要）

10層ごと（`BOSS_INTERVAL = 10`、暫定）の階を **ボス階** とし、進行の壁にする。

- **ボス階の挙動**: 第10・20・30…階に固定の強敵（階層ボス）が待つ。ボスは [02](./02-exploration-mapping.md) のFOE系として配置するか、階の最奥に固定遭遇として置く。
- **ゲート（壁）**: ボスを撃破するまで **次の帯（次の10層）へ進めない**。これが「中間型」の明確な区切りを作る。
- **撃破報酬**:
  1. 次の帯への進行解放
  2. その階への **ワープチェックポイント解放**（§5）
  3. 良質な装備・素材・所持金などの報酬
- **再戦**: 撃破済みボスは再戦可能（ファーム用）にしてよい。スケーリングは固定（その階の難度）。
- **ゲート（封鎖）の実装ルール**: ボス階（例: 第10階）の **出口階段を、`BossGateState.defeated === false` の間は使用不可** にする。地形 `generated` 自体は書き換えず、**遷移時にゲート判定を挟む**（出口階段セルに乗って「上る」操作をしたとき、未撃破なら「強大な力に阻まれる」等で拒否）。これにより再訪・再生成の整合を保つ（封鎖は地形でなく状態で表現）。ボスは出口階段の手前の部屋に固定遭遇として置き、通り抜けるには戦う導線にする。

```ts
interface BossGateState {
  depth: number;       // 10, 20, 30, ...
  defeated: boolean;   // 撃破で「出口階段の封鎖解除」＋「ワープ解放」
}
// 出口階段の通行可否：canAscend(depth) = !isBossFloor(depth) || bossGates[depth]?.defeated
```

> **設計判断**: ボス階を「ワープ解放」「進行解放」「報酬」の3つの節目に一致させることで、プレイヤーの目標（次のボスを倒す）と区切り（ワープ・補給）が自然に揃う。封鎖を地形でなく状態で持つことで、生成済み地形を一切書き換えずにゲートを表現できる。

## 5. ワープチェックポイント（10層ごと）

到達済みの区切り階へ、拠点から直接ワープできる。

### 仕様

- **解放条件**: その区切り階のボスを撃破（＝チェックポイント到達）。
  - 第10階ボス撃破 → 第10階へワープ可能
  - 第20階ボス撃破 → 第20階へワープ可能（以降同様、無限）
- **ワープ起点**: 拠点（街）の **ワープ装置**。
- **行き先の選択**: 解放済みチェックポイントなら **任意に選んで** 飛べる（最深だけでなく、下層を選んでファーム・採集も可能）。
- **帰還**: タワー内からは帰還アイテム（アリアドネの糸相当）で拠点へ戻る。全滅時も拠点へ戻る（§6）。
- **当初の「フロアジャンプ」を本仕様に統合**: [02](./02-exploration-mapping.md) のフロアジャンプ（マップ完成で次階へ）は廃止し、この10層ワープに一本化する。

```ts
interface WarpState {
  unlockedCheckpoints: number[]; // [10, 20, 30, ...] 撃破済み
}
// 拠点のワープ装置で unlockedCheckpoints から行き先を選択
```

## 6. 全滅・帰還（ソフトペナルティ）

- **全滅時**: パーティが全滅しても **拠点に戻されるだけ**。キャラ・装備・所持金・アイテム・経験値は **失わない**。
- **失うもの**: そのダイブ（潜行）の進行＝現在の階の位置。次回はワープで最深チェックポイントから再開する。
- **途中帰還**: 帰還アイテムでいつでも拠点へ。獲得物は保持。
- **オートセーブ**: 全滅・帰還・階層移動・ボス撃破などの区切りで自動保存（[05](./05-progression-meta.md)）。手動ロストの概念はないので、セーブは安全側に倒す。

> **設計判断**: 「ロスト無し」により、気軽に何度でも挑戦できるスコアアタック体験にする。リスクは「時間」だけ。難易度は敵スケーリングと階層ボスで担保する。

## 7. 目的・スコア（ストーリーの代替）

ストーリーが無い代わりに、以下を恒常的な目標として提示する。

1. **最高到達階の更新（スコアアタック）**: 最深踏破階・最高撃破ボス階を記録し、ベスト更新を主目的にする。
2. **階層ボス撃破**: 各区切りボスが短期目標。撃破履歴を残す。
3. **ビルド構築の追求**: 種族×職業×スキル×称号×装備（[01](./01-character-system.md)・[03](./03-battle-system.md)・[04](./04-items-equipment-crafting.md)）で、より深く登れる編成を磨く。

```ts
interface TowerRecord {
  deepestReached: number;     // 最深踏破階
  highestBossDefeated: number; // 最高撃破ボス階
  totalDives: number;          // 挑戦回数
  bossDefeatLog: { depth: number; at: number }[]; // 撃破履歴
}
```

> コレクション（図鑑・装備収集）は主目的には選ばれなかったが、**任意のやり込み要素**として残してよい（[05](./05-progression-meta.md) の図鑑）。

## 8. システム解放トリガー（ミッションの代替）

ストーリーミッションでの解放（[01](./01-character-system.md)・[05](./05-progression-meta.md)）は廃止し、**到達階・ボス撃破** をトリガーにする（数値は暫定）。

| システム | 解放トリガー（暫定） |
| --- | --- |
| 種族・職業の選択 | **作成時から自由**（全体ゲートなし）。基本職業は初期から選択可能（[01 §4](./01-character-system.md)） |
| 条件付き職業の解放 | 職業ごとに個別の到達階等を設定可能（今後定義。解放前は選択肢に出さない） |
| 10層ワープ | 各区切りボス撃破（§5） |
| 称号（第2スキルツリー） | 第20階 or 第30階到達 |
| 転生 | レベル30以上（据え置き。[01](./01-character-system.md)） |

## 9. まだ決めるべき項目（未決事項）

以下は本書で **暫定値・暫定方針** にしてある。プレイテストや好みで確定したい論点。これらの確定とマスターデータの拡充は **Phase 6（コンテンツ拡充・バランス調整、[README](./README.md)）** でまとめて行う。

1. **敵スケーリングと育成カーブの具体数値**: §3 の `k`、経験値必要量、Lv1〜100のステータス成長式。レベル上限が100なので、その範囲でのカーブと敵の伸びの相対関係を決める。最も重要なバランス調整。
2. **レベル上限100 × 無限スケーリングの帰結（重要）**: キャラのレベルは100で頭打ち、転生ボーナスも有限（最大 全能力+20・非累積）なのに対し、敵は無限に強くなる。したがって **育成の伸びしろ（レベル＋転生＋装備/鍛冶＋スキル振り）には事実上の上限があり、いつかは敵に追い抜かれて到達階に天井が生まれる**。これはスコアアタック（最高到達階の更新）と整合するが、「中間型（育てれば進める）」をどこまで維持するかは、装備・鍛冶のスケール（§4・項4）と転生サイクルの調整で決める。深層攻略の主役を「レベル」ではなく「装備ティア＋ビルド最適化」に寄せるのが妥当。
3. **SP の使い道**: レベル上限100で取得SPは有限。全スキル取得には複数回の転生（ボーナスSP）が要る想定。全取得後の余剰SPをどう扱うか（① 小さなステータス強化に変換、② 貯まるだけ、③ スキル強化上限の引き上げ）。
4. **階層ボスの間隔**: `BOSS_INTERVAL = 10` をワープ間隔と一致させているが、ボスをもっと細かく/粗く置くか。
5. **装備・鍛冶のスケール**: 鍛冶+5上限（[04](./04-items-equipment-crafting.md)）を据え置き、装備は10層帯ごとのティアで更新する想定。深層用の装備供給をドロップ主体にするか鍛冶主体にするか。レベル上限がある分、**深層攻略の伸びしろの主役は装備**になりやすいため重要。
6. **採集・食材・料理を残すか**: 無限タワーでも探索の補給計画として機能する想定で **残す方針（暫定）**。不要なら削る。
7. **下層ファームの意味づけ**: ワープで下層に戻れるが、下層を周回する意味（素材・経験値効率）をどう設計するか。深層偏重だと下層が無価値になる。
8. **タワーのテーマ変化**: 10層帯ごとに見た目・ギミックのテーマを変えるか（雰囲気の単調化対策）。グラフィックは作り込まない方針（[README](./README.md)）なので、配色・床タイプ・敵の組み合わせで表現する程度。
9. **挑戦の節目演出**: ベスト更新時・ボス撃破時のフィードバック（スコア表示・実績）。
